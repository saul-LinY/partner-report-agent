# 采集器本机验证：CC Switch 原始解析链路

日期：2026-10-28。结论：核心会话读取、提问／正式回复分离已有本机实测证据；仍需实现正式客户端和服务端接收链路。

## 验证方式与授权范围

本次没有用另一套语言重新写格式解析器，也没有将界面演示数据当成验证结果。

直接编译 CC Switch 4.0.21（`6d6b7162f122ac0ce1356a14688c8c4f712db3c8`）的原始 Rust provider、统一消息模型和共享辅助模块，调用各自的 `load_messages` 路径读取本机文件。原始模块未修改，通过编译时路径引用；校验了源码哈希。目录 getter、外围模型和调用入口由隔离验证程序适配，不启动 CC Switch 的完整应用或全量正文扫描。

本机已安装的 CC Switch 也是 4.0.21。此次没有通过点击其界面导出数据，而是直接运行与该版本对应的读取核心，验证未来独立采集器所需的能力。

以用户本轮授权的 `partner-report-agent` 项目根目录作为临时验证白名单，未修改系统中的正式审批记录。其他项目仅参与必要的目录／数据库定位元数据查询，不提取或导出其会话正文。源数据库以普通只读模式打开；不调用删除、恢复会话、历史迁移或配置写入。

“只读定位字段”指不提取或实例化正文，不意味着 JSONL 缓冲或 SQLite 数据页中没有邻接正文的字节。严格的字节级隔离仍受 [源码调研报告](SESSION_COLLECTOR_RESEARCH.md) 中所述存储布局限制。本次不将它宣称为已经完成的生产隐私验收。

构建工具链及验证代码位于 Git 已忽略的 `.local/collector-probe/`，未修改用户的全局 PATH 或 shell 配置。真实提问和回复只保存在该私有目录，不进入本报告或版本库，未上传到局域网系统或外部服务。

| ----------- | -------------: | -------: | -------------: | -----------------: |
| Codex       |            153 |    1,230 |          1,094 |                136 |
| Claude Code |              5 |       31 |             20 |                 11 |
| Oh My Pi    |              1 |       13 |              9 |                  4 |
| 合计        |            159 |    1,274 |          1,123 |                151 |

这里的“文件”不是会话数：Codex 125 条普通会话元数据关联了 154 份候选文件，其中 1 份因跨出当前项目白名单被阻止正文解析；其余 153 份文件属于 124 个会话。加上 Claude 的 5 个会话、OMP 的 1 个会话，共覆盖 130 个会话身份。

- 在 Codex 元数据中另外识别出当前项目的 137 条子代理记录，本轮未读取其正文。
- 文件名和目录盘点发现额外 29 份历史／续接文件。与只读取数据库当前指向文件相比，多提取了 260 轮，说明历史补传不能只读当前 rollout。
- 1,274 轮按工具、原始会话身份和稳定轮次身份生成 1,274 个键；本次样本没有使用纯序号 `tN` 作为持久身份，也没有同键重复轮次。不能据此推论其他版本或分叉样本永远不会重复。
- OMP 文件名包含时间前缀，与头部真正的会话 ID 不同；接收仿真使用头部 ID，而不是文件名。
- 所有进入允许范围且可解析的真实文件均返回结构化结果，没有格式解析异常。

## 提问、正式回复与过程的分离

Codex 的 1,094 条已接受回复都带有明确 `final_answer` phase；Claude 的 20 条和 OMP 的 9 条使用原生终止原因判断。没有将 `commentary` 或仍在工具调用中的文字提升为正式回复。

额外写了独立的原始记录核对逻辑，不以 CC Switch 的展示投影作为唯一依据：1,123 条已接受回复都能在相应源文件的原生终止消息中找到完全相同的文本，未发现原文不一致。该检查证明文本来源和完整性，不等同于人工逐条审阅了所有提问与回复的语义配对。

实际解析过程中还识别出 16,676 个 thinking 块、18,647 个工具调用及同样数量的工具结果；这些结构不进入提问／正式回复的输出契约。来源中的图片没有随本次文本输出导出，附件采集与上传范围仍未确定。

151 轮没有接受为正式完成，原因如下：

| 原因                                  | 轮次 |
| ------------------------------------- | ---: |
| 明确中断                              |  113 |
| 没有正式回复文本                      |   30 |
| 只有过程说明                          |    2 |
| Claude 客户端合成的占位或接口错误提示 |    6 |

真实样本的最大已接受回复为 5,761 字符。另用超过 8,192 字符的合成回复验证完整保留，避免把“真实样本恰好不长”误认为已经测过长文边界。

## 实际发现并处理的问题

### Claude 的错误提示会看起来像助手回复

6 条 Claude 候选回复的原始 `message.model` 为 `<synthetic>`，`stop_reason` 为 `stop_sequence`。核对后发现分别是无须回复的客户端占位，或接口错误提示，不是模型正式答复。

CC Switch 会在统一模型中去掉 `<synthetic>` 模型名；仅依据统一模型的“最后一段助手文字”会丢失这个诊断信号。验证程序通过原始记录 UUID 与该模型标记关联，标记 `provider_diagnostic`，只保留对应提问，不上传诊断文本作为正式答复。

另加一个终止原因为 `end_turn` 的合成错误样例，验证不能只依赖结束原因绕过这项过滤。

### 一个会话可能跨出项目根目录

一份 Codex 文件的目录元数据跨出本次允许根。验证程序在调用正文解析器前检查定位记录，发现越界后停止该路径并跳过整份正文提取。没有因为它的初始项目或数据库 cwd 属于本项目，就将整份历史收入。

正式产品应进一步定义 Git worktree、显式目录切换和已批准项目别名的映射；本次采取保守的根目录匹配，不把它当成已解决所有跨项目归属问题。

### 不能只读当前文件，也不能使用文件名或第几轮作为主键

Codex 的额外历史文件、OMP 的带时间文件名、Pi/OMP 分支都说明需要保留工具原生身份。验证程序使用原生轮次 ID，或真实提问消息 ID；分支切换可更新同一提问下的回复。

本次真实样本中没有触发纯序号回退；没有稳定源身份的旧格式仍需后续设计，不能直接上线用轮次序号代替。

## 增量、重试、队列及其他来源验证

29 项检查全部通过，机器可读结果见 [验证摘要](research/cc-switch/local-validation-summary.json)。以下包含受控合成样例及本地 SQLite 接收仿真，不应描述为生产网络验收。

| 验证                      | 结果及范围                                                                                 |
| ------------------------- | ------------------------------------------------------------------------------------------ |
| 六个主要工具的原始解析器  | Codex、Claude、OMP 有真实会话；Pi、OpenCode、Hermes 的本项目样本未发现，使用隔离格式样例   |
| 未批准项目不打开正文源    | 使用不存在的源文件作为哨兵；拒绝或根目录不匹配时在 open 前返回，而不是读取后过滤           |
| 未完成后补正式回复        | Codex、Pi、OMP 的源格式样例保持同一轮 ID，3 条接收记录从未完成更新为完成，记录数量不增加   |
| 活动分支切换              | Pi、OMP 同一提问的回复被新分支替换，不混入旧分支文字，不新增提问记录                       |
| 真实数据接收仿真          | 1,274 轮写入独立 SQLite 接收表；同一批次重试不增加记录，也不改变已确认数据                 |
| 离线队列持久化            | 把待传原文保存到独立 outbox，关闭并重开数据库后恢复，再接收确认；确认后才推进队列          |
| 正文不截断                | 超过 8,192 字符的 Claude 回复在解析、队列和接收存储后与原文完全一致                        |
| 非正文过滤                | 注入上下文、sidechain、meta、工具结果、thinking 和接口诊断标记均不进入提问／正式回复输出   |
| Hermes 正式结束的不确定性 | 解析器可以输出候选最后回复，但没有足够完成证据的样例不擅自标为完成；该来源仍需真实样本验证 |

OpenCode 的本机数据库是有会话及消息记录的，并非工具无数据；但本次定位元数据没有匹配到授权项目，因此没有为了补齐覆盖率读取别的项目。Hermes 和 Pi 同理按本次默认目录及定位范围判断，不把未找到授权样本描述为它们没有会话。

本轮真实文件的解析加原始文本核对累计约 12.6 秒，使用本机调试构建、包含压缩文件读取；这不是完整应用扫描、调度、网络上传或大规模团队数据的性能承诺。

## 哪些已经有证据，哪些仍需工程实现

已经有证据：不依赖 CC Switch 完整应用的 Rust 读取核心可以处理本机主要工具数据；可以区分真实提问、正式回复、未完成状态和过程块；有稳定来源身份时，补传及幂等更新可实现。

仍未验证或实现：

- 其他来源的本机获准真实样本；尤其 Hermes 的可靠完成信号、不同版本存储差异和其余七个 provider。
- 正式审批服务的同步、撤销、跨设备及重命名规则。本次临时白名单没有替代这部分。
- 原文 HTTP 接收接口、真实断网／超时／部分成功、服务端存储修订和中央模型任务。SQLite 仿真不代表现有生产接口已支持原文。
- macOS 菜单栏壳、登录自启、系统休眠／唤醒、目录授权、签名、升级与队列恢复。
- 附件和旧分支归档策略，以及源文件在首次读取前就被工具清理的不可恢复情况。

因此，可以进入独立 Rust 采集核心和隔离服务端的实现阶段；不能把本次验证当成整个 App 已达到可发给成员使用的状态。
