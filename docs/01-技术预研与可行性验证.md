# 01 技术预研与可行性验证

> 对应 PRD：6、20 Phase 0、21 AC-01 至 AC-08 的最薄验证、23。
>
> 前置依赖：无。

## 1. 目标

在进入正式工程实现前，用可运行 Spike 消除五类最高风险：Codex 本地读取、Hook 可靠性、增量提取质量、飞书交互闭环、身份与隐私边界。

本板块只验证能力和契约，不追求生产级 UI、吞吐、容灾或完整领域模型。

## 2. 验证项

### 2.1 Codex Plugin 与 Hook

验证内容：

1. 本地测试 Plugin 可安装、启用、升级和卸载。
2. Plugin 能携带 Skill、Hook 配置以及访问服务端所需的连接能力。
3. 非托管 Hook 的审查和信任流程可被 Partner 理解并完成。
4. `Stop` 可读取 `session_id`、`turn_id`、`cwd`，只做本地快速入队。
5. `SessionEnd` 只作为阶段性信号；主线程结束、空闲、归档等场景分别记录行为。
6. Hook 超时、未信任、脚本异常和重复触发不会影响 Codex 主流程。

当前官方文档给出的关键边界必须进入测试：

- `SessionEnd` 仅适用于主线程，默认超时 1 秒、最大 3 秒。
- `SessionEnd.reason` 当前只有 `other`，不能用于业务分类。
- `transcript_path` 是便利字段，不是稳定解析协议。
- `Stop` 输出必须符合 Hook 协议；采集 Hook 应成功静默退出，不能阻断 Turn。

### 2.2 App Server 线程读取

使用真实本地测试数据验证：

- `thread/list` 的分页、活跃/归档筛选、`cwd` 和时间元数据覆盖。
- `thread/read(includeTurns)` 的完整 Turn 顺序、工具项、异常项和大 Session 表现。
- Session 恢复后 ID 和 Turn 追加行为。
- Session 删除、历史关闭、不可读和仍活跃状态的可检测性。
- 读取 10、50 个 Session 的耗时与内存基线。

只把稳定公开方法纳入 MVP 主路径。实验性分页方法可以做对比，不作为 v1 必需依赖。

### 2.3 Scheduled Task 和补偿扫描

验证每日本地任务能够调用 Plugin Skill 或扫描命令，并记录以下约束：

- 访问本地文件时电脑必须开机、桌面应用必须运行、项目目录必须仍可用。
- CLI 和 IDE 不提供 Scheduled 管理入口。
- 无人值守任务受默认权限与网络规则约束。
- 错过执行时间后，Plugin 自身必须依据 `last_scan_at` 补扫，而不能假设平台自动补跑。

### 2.4 离线提取与聚类

建立首版脱敏评测集，至少包含：

- 讨论但未执行。
- 计划、执行中、待验证、完成、阻塞、取消。
- 同一事项跨多个 Session 推进。
- 一个 Session 包含多个事项。
- 无关、个人和敏感内容。
- Session 恢复后新增 Turn 改变状态。
- 证据不足但语言看似“完成”的反例。

输出 `SessionWorkFact v1` JSON，并测量：Schema 有效率、工作相关性精确率、状态识别、完成结论证据覆盖、敏感内容拦截率、聚类误合并/漏合并。

### 2.5 飞书卡片与回调

用测试企业应用验证：

- JSON 2.0 卡片发送、按钮、表单、输入框、分页和局部更新。
- 回调验签、身份字段、重复回调和超时重试。
- 回调快速确认后异步更新卡片。
- 旧版本卡片提示和无交互的 Monitor 最终消息。
- 文件上传、PDF 附件发送以及返回的文件 Key、消息 ID。

### 2.6 身份与隐私薄链路

验证设备码或 OAuth 绑定流程能建立：

```text
tenant_id + partner_id + feishu_open_id + plugin_instance_id
```

用脱敏 Session 打通一条薄链路：本地读取 -> Fact JSON -> 测试服务 -> Work Item -> 飞书确认 -> 个人 Report 草稿。服务端和飞书均不得出现完整 transcript。

## 4. 需要冻结的决策

Phase 0 结束前必须明确：

1. Plugin 与服务端的实现语言、最低运行时和打包方式。
2. 本地 Outbox/Cursor 存储方案以及崩溃恢复方式。
3. 中心服务是模块化单体还是多服务；MVP 推荐先保持模块边界清晰，避免过早拆分部署单元。
4. 关系数据库、队列、对象存储和任务执行器选择。
5. 模型供应商、模型版本管理、预算、延迟和数据驻留边界。
6. Evidence Excerpt 默认开关、最大长度和脱敏策略。
7. 飞书企业自建应用权限集合和测试/生产应用隔离方式。

## 5. 测试记录模板

每个验证项都要记录：

| 字段 | 内容 |
| --- | --- |
| 假设 | 希望验证的能力或限制 |
| 环境 | Codex/OS/Plugin/飞书应用版本 |
| 输入 | 测试 Session 或事件 |
| 步骤 | 可重复执行的命令和操作 |
| 观察 | 实际输出、耗时、失败行为 |
| 结论 | 通过、受限、失败 |
| 工程影响 | 后续设计和降级方案 |

## 6. 退出标准

只有全部满足才进入板块 02：

- 从至少 10 个脱敏 Session 中稳定读取 Turn，并识别活跃、归档、删除/不可读差异。
- 同一 Session 新增 Turn 时只处理增量，旧 Fact 不重复生成。
- Hook 操作在限制时间内完成，失败时补偿扫描能发现 Session。
- 提取结果通过 JSON Schema；“完成”结论均有证据或不确定标记。
- 飞书卡片回调可在 2 秒内给出接收反馈，耗时任务异步完成。
- 薄链路可生成并审核一份个人 Report 草稿。
- 完整 transcript 未离开本地，敏感样本未进入日志或卡片。
- 所有关键不确定项都有 ADR、降级方案或明确阻塞结论。

## 7. 不通过时的处理

- App Server 无法稳定覆盖 Session：停止正式开发，重新定义数据源边界，不以 transcript 格式硬顶生产方案。
- Hook 不可靠但 App Server 扫描可用：Hook 降级为活动信号，Local Runner 的 2 小时静默检查与启动/每 6 小时补偿扫描成为正确性主路径。
- Scheduled Task 不能满足试点环境：增加启动补扫和手动同步，明确 SLA 不承诺准时后台执行。
- 飞书复杂编辑体验不达标：保留卡片单项审核，将批量复杂编辑推迟到 Web 工作台。
- 本地模型质量或性能不达标：重新评估“本地提取”的执行载体，但不得默认上传完整 transcript。
