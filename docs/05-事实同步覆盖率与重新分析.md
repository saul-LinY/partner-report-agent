# 05 事实同步、覆盖率与重新分析

> 对应 PRD：7.2、7.4、9.2、FR-02、FR-03、FR-07、16.2、19、AC-02、AC-02A、AC-07。
>
> 前置依赖：02、03、04。

## 1. 目标

可靠接收 Plugin 上传的结构化事实，形成可追踪 Coverage，并通过 Local Runner 每次心跳周期的租约轮询完成服务端无法直接触达设备的 Re-analysis 闭环。

## 2. Ingestion API

`POST /v1/session-facts/batch`

请求头：短期 Plugin Token、`Idempotency-Key`、压缩标记。请求体：

```json
{
  "schema_version": "1.0",
  "extractor_version": "extractor-v1",
  "plugin_instance_id": "pi_123",
  "batch_id": "batch_123",
  "period_candidates": ["2026-W31"],
  "sessions": []
}
```

单 Session 项必须包含 `session_id`、Turn 范围、source revision/hash、事实列表、Coverage 状态和本地生成时间。

## 3. 校验顺序

1. 验证 Token、Binding active、Instance 和最低版本。
2. 从认证上下文确定租户和 Partner，忽略请求体试图覆盖的主体。
3. 检查 Schema/Extractor 版本兼容。
4. 校验批次和 Session 项大小、Evidence 长度与敏感字段。
5. 使用 `(tenant, partner, session, source_revision, fact_id)` 幂等写入。
6. 计算受影响周期并更新 Coverage 投影。
7. 写入审计事件，并记录本批 Fact 要等到本周 `cutoff_at` 后再参与聚合；普通同步不创建聚合任务。

任何日志只记录 ID、大小、版本和错误码，不记录 Evidence 正文。

## 4. 部分成功语义

批次响应按 Session 返回：

```json
{
  "batch_id": "batch_123",
  "accepted": 8,
  "rejected": 1,
  "results": [
    { "session_id": "thr_1", "status": "accepted", "revision": 3 },
    {
      "session_id": "thr_2",
      "status": "rejected",
      "code": "SCHEMA_INVALID",
      "retryable": false
    }
  ]
}
```

- 一个 Session 失败不能回滚其他有效 Session。
- 相同幂等键和相同 Payload 返回原结果。
- 相同幂等键但 Payload 不同返回冲突。
- Plugin 只确认 accepted 项；rejected 项按 `retryable` 决定重试或隔离。

## 5. Fact 版本和更新

- 新 Turn 产生新 source revision，并可新增 Fact 或更新同一 Session 内候选事项的状态链。
- 不原地删除旧 revision；维护 current 投影和 revision 历史。
- 内容相同且 hash 相同的重传不产生重复 Fact；所有有效 revision 在周截止时统一进入聚合输入。
- 提取器升级重跑用新 extractor revision，旧版本保留用于审计和比较。
- Partner 后续排除 Session 时，Fact 从可用投影中撤下并触发受影响聚合重建。

## 6. Coverage 服务

Coverage 按 `partner_id + period_id` 汇总：

```json
{
  "discovered": 14,
  "readable": 13,
  "extracted": 12,
  "failed": 1,
  "excluded": 1,
  "active_at_cutoff": 2,
  "warnings": ["SESSION_DELETED"],
  "last_sync_at": "..."
}
```

不变量：

- `discovered = readable + failed_read + excluded`，具体公式以状态字典冻结为准。
- `extracted <= readable`。
- Pending 不得显示为成功。
- 每个 Warning 可定位到内部 Session 状态，但对飞书只暴露最小必要说明。
- 报告生成保存 Coverage Snapshot，不随未来同步漂移。

## 7. Re-analysis Job

创建条件：范围扩大、深挖新主题、证据不足、提取器升级。

```text
PENDING -> LEASED -> RUNNING -> COMPLETED
                     |  -> RETRY_WAIT -> PENDING
                     |  -> FAILED
PENDING/LEASED -> CANCELLED
```

Job 字段：

```text
job_id, tenant_id, partner_id, plugin_instance_id
reason, requested_scope, requested_topic, extractor_version
idempotency_key, status, lease_owner, lease_until
attempt_count, max_attempts, expires_at, result_revision
```

相同 Partner、Review、Scope、Reason 和目标 extractor version 生成稳定幂等键，避免重复卡片点击创建多个任务。

## 8. Plugin 轮询协议

Runner 默认每 5 分钟轮询；普通 Session 提取受 120 分钟静默窗口约束，服务端 Re-analysis/Rescan Job 和 Admin 立即重扫可以显式携带 `bypass_quiet_window=true`。周截止本身由中央 Worker 调度，不等于某个 Session 的静默窗口到期。

- `GET /v1/sync-jobs/pending?limit=N`
- `POST /v1/sync-jobs/{id}/ack`
- `POST /v1/sync-jobs/{id}/complete`
- `POST /v1/sync-jobs/{id}/fail`

`ack` 原子取得租约并返回 job token。只有目标 active instance 可以领取。租约到期后任务可再次领取；旧 lease 的 complete 被拒绝或按已完成幂等结果处理。

Complete 只接受已成功上传并可引用的 `result_revision`，不能先标完成再上传事实。

## 9. 审核联动

当审核变更需要重新分析：

1. Review Engine 创建 Job 并把变更设为 `WAITING_LOCAL_REANALYSIS`。
2. 飞书显示“等待本地 Codex”，提供立即同步和取消入口；普通流程无需 Partner 打开 Codex 手动执行命令。
3. Job 完成触发 Fact 投影和 Work Item 重建。
4. 新版本生成 Change Preview，不自动应用 Partner 原修改。
5. 超时或失败显示真实状态，不宣称已修改。

## 10. 重试与限流

- Ingestion：网络和 5xx 指数退避；Schema/权限错误不自动重试。
- Job：租约超时重试，超过最大尝试进入 `FAILED`。
- 对 Instance、Partner 和 Tenant 分级限流，批量大小可配置。
- 普通上传不触发下游聚合；中央 Worker 在每个周周期截止后只创建一个幂等聚合任务，避免任务风暴。
- 队列积压时接受上传但明确延迟，不丢弃事实。

## 11. 测试

- 批次全部成功、部分成功、全部失败和响应丢失重试。
- 重复幂等键、冲突 Payload、重复 Fact、乱序 revision。
- 被撤销/跨 Partner Instance 上传。
- 不兼容 Schema、过旧 Plugin、超长 Evidence 和压缩炸弹限制。
- Coverage 各状态组合、截止快照和未来 revision 不改变历史 Snapshot。
- 两个轮询者争抢同一 Job、租约过期、旧 lease complete。
- Job 完成前上传失败、取消和超时。
- Re-analysis 完成后审核数据生成新版本而非静默覆盖。

## 12. 指标与审计

指标：批次/Session 接收率、去重率、字节量、Evidence 截断、版本分布、Coverage 差距、Job 等待/执行时间、租约重领和失败率。

审计：Fact revision 接收、Session 排除/恢复、Coverage Snapshot、Job 创建/领取/完成/取消、敏感校验拒绝。

## 13. 验收与退出标准

- 50 个 Session 的增量批次可在目标时间内接收，单项失败不丢弃其他项。
- 重传和响应丢失不会重复创建 Fact。
- Coverage 数量一致，缺口和离线状态可见。
- Re-analysis 只能由目标 Plugin 领取，支持幂等、租约、取消、超时和重试。
- Job 完成后能驱动新 Work Item/Preview 版本。
- 满足 AC-02、AC-02A、AC-07 的服务端部分。
