# 12 端到端测试、试点与发布

> 对应 PRD：20 至 24、27，统一验收 AC-01 至 AC-12。
>
> 前置依赖：01 至 11。

## 1. 目标

用自动化 E2E、AI 评测、性能/可靠性测试、安全测试和真实小团队试点证明主链路成立，并建立可回滚、可观测的发布流程。

## 2. 测试环境

至少划分：

- Local：开发者本地和脱敏 Fixture。
- Integration：真实数据库/队列/对象存储替代环境，模拟飞书和 AI Provider。
- Staging：独立飞书测试应用、真实 Codex 桌面端/Plugin、脱敏真实 Session。
- Pilot/Production：受控 Partner 范围、生产凭证和正式保留策略。

不同环境的 tenant、飞书应用、OAuth Client、对象存储和密钥完全隔离。测试数据不能复制生产原始 Session。

## 3. 测试数据

建立版本化场景库：

- 讨论、计划、执行、待验证、完成、阻塞、取消。
- Session 恢复、Hook 遗漏、仍活跃、删除、历史关闭。
- 2 小时静默窗口顺延、提取中新增 Turn、Runner 崩溃/重启和心跳中断。
- 同一任务跨 Session、相似任务不同项目、多事项同 Session。
- Partner 修改、补充、排除、merge/split、时间范围扩大。
- 跨周期新增、推进、完成、阻塞出现/解除、无更新和范围变化。
- 敏感信息、密钥、大段代码、Prompt injection 和跨租户攻击。
- 飞书重复回调、旧卡片、限流、文件/消息部分失败。

每个 Fixture 配置预期 Fact、Work Item、Review 结果、Report Claim 和 Coverage。

## 5. 最小演示场景

严格实现 PRD 第 27 节：2 个 Partner、1 个 Monitor、2 个公共项目、1 个独立事项。

自动化/脚本化步骤：

1. 两个 Plugin Instance 分别读取多个 Session 并上传 Fact。
2. Partner A 确认 3 项、排除 1 项、补充 1 个完成结果。
3. Partner B 改时间范围，创建并完成一次 Re-analysis。
4. 两人分别审核并提交个人 Report。
5. 团队聚合合并公共项目并保留独立调研。
6. 与上期比较得到一个完成和一个新增阻塞。
7. 生成飞书正文和 PDF，幂等发送给 Monitor。
8. 断言 Monitor 消息无审核、修改、追问和下钻入口。

演示需要保存 Trace ID、对象版本、关键截图、PDF 和验收报告，不能只依赖现场口述。

## 6. AI 与规则评测门禁

离线评测在每次 extractor、Prompt、模型、聚类器、Comparator 变更时运行：

- Schema 有效率。
- 相关性、状态、完成证据和敏感过滤指标。
- 聚类误合并/漏合并、项目归属和稳定 ID。
- NL Change Parser 操作/参数准确率和澄清率。
- Report/Team Report Claim 来源覆盖和事实一致性。
- 跨周期匹配与变化分类。

版本升级只有在关键指标不回退且成本/延迟可接受时灰度。具体阈值以 Phase 0 基线和产品容忍度 ADR 冻结。

## 7. 性能测试

基准规模：单 Partner 50 个 Session、团队试点 Partner 数和合理峰值回调/提交并发。

验证：

- 本地增量同步 10 分钟目标。
- 卡片接收反馈 2 秒目标。
- 普通重新聚合 60 秒目标。
- 批量部分失败、队列积压和限流下的恢复。
- 长 Session、最大 Evidence、最大 Work Item 和 PDF 页数。
- 团队截止时多 Partner 同时提交的峰值。

报告 p50/p95/p99、资源、模型成本和瓶颈；不要只报平均值。

## 8. 故障演练

在 Staging 注入：

- Plugin/桌面应用离线和任务错过。
- Local Runner 未启动、重复实例争抢、提取中崩溃和休眠后补跑。
- Hook 未信任/超时。
- App Server 读取失败或 Session 删除。
- 上传响应丢失和重复批次。
- Worker 在 Preview/Apply、生成、渲染、交付中间崩溃。
- 飞书回调重放、限流、文件成功消息失败。
- AI Provider 超时/Schema 无效。
- 数据库只读、队列/对象存储短时不可用。

每项断言：不丢数据、不越权、不假成功、可补跑、无重复成功效果、告警触发、Runbook 可执行。

## 9. 试点方案

### 9.1 范围

首批 3 至 5 名内部 Partner，一个 Team Admin，一个 Monitor，持续至少两个完整周报周期，以便验证跨周期比较。

### 9.2 准入

- macOS Codex 桌面端、主要单设备。
- 同意隐私说明和授权范围。
- 飞书应用权限已审批。
- 提供可脱敏的历史/当前 Session。
- 明确试点不用于个人绩效评分。

### 9.3 观察指标

- 安装/绑定成功、Coverage 和同步失败。
- 审核中位时间是否 <= 10 分钟。
- 按时提交率是否 >= 90%。
- Work Item 删除、merge、状态/事实修正。
- 飞书闭环修改占比是否 >= 80%。
- 重新分析比例、生成/渲染/交付失败。
- 用户报告的遗漏、错误和隐私问题。

每周期复盘只用聚合指标，避免形成个人绩效视图。

## 10. 发布与回滚

发布顺序：兼容性数据库迁移 -> 服务端/Worker -> Admin 配置 -> Plugin 小批版本 -> 飞书模板 -> 目标 Partner 灰度。

要求：

- Plugin/Schema 至少 N-1 兼容，最低版本策略有宽限期。
- GitHub Marketplace 固定稳定 Release；兼容升级验证 `PLUGIN_DATA`、Cursor、配置、Plugin Instance 和 Keychain Token 均保留。
- Feature Flag 控制提取器、聚类器、报告模板和交付。
- AI/Prompt/规则均有版本 pin 和快速回退。
- 数据迁移采用扩展/迁移/收缩，不依赖破坏性回滚。
- 关闭自动交付不影响个人报告提交；必要时人工审批 Team Report 的 Deliver 操作，但不引入 Monitor 审核。

## 11. 上线检查清单

- 24 节待确认决策中，保留、Evidence、模板、周期、数据源、模型和飞书应用均已有负责人签字。
- 全部 AC 测试通过并附证据。
- 安全评审、隐私评审、威胁模型和删除演练通过。
- Dashboard、告警、值班人和 Runbook 就绪。
- 备份恢复和交付对账演练通过。
- 飞书生产目标发送测试成功。
- Plugin 安装、信任、升级、撤销文档可供 Partner 使用。
- 试点参与者和 Support 知道 Coverage Warning 与离线限制。

## 12. 退出标准

MVP 主链路成立需要：

- 最小演示场景完整通过。
- 试点至少两个周期，无跨 Partner/跨租户越权和敏感数据泄露。
- 成功标准中的审核时间、提交率、来源覆盖、飞书闭环和交付可测量；未达标项有明确阻塞和修复计划。
- 关键 AI/规则指标不低于冻结阈值。
- 故障注入证明系统不丢数据、不假成功并能恢复。
- 发布、回滚、补跑、删除和应急响应均有可重复执行记录。

达到以上条件后进入受控 MVP 发布；Web 批量审核、月报、外部证据源和更多附件格式转入 Phase 3 Backlog。
