# 09 团队聚合与跨周期比较

> 当前状态：后续路线。当前实现只聚合单个 Partner 的项目进展并在数据中台展示。

> 对应 PRD：9.5、9.6、FR-09、FR-10、14.6、AC-09、AC-10。
>
> 前置依赖：08。

## 1. 目标

仅使用已提交个人 Report 的结构化数据生成团队项目状态，保留无法可靠归类的独立工作，并通过结构化匹配识别相对上期的真实变化。

## 2. 周期触发

团队截止时创建一次聚合 Run：

1. 固定 Team 配置、Project 映射和截止时间版本。
2. 获取截止时 `SUBMITTED` 的 Individual Report ID/版本。
3. 记录未提交 Partner 和提交者 Coverage 状态。
4. 创建不可变输入清单与 checksum。
5. 异步聚合，生成 `TeamReportDraft`。

未提交成员只进入 `submission_coverage`，不能使用其草稿或 Work Item 替代。

## 3. 输入模型

团队聚合读取：

- Individual Report 的结构化 achievements、project progress、risks、next priorities、monitor actions。
- 其 Work Item Snapshot 引用和稳定 ID。
- Team Project/alias/external ID 配置。
- 上期已锁定 Team Report 和 Individual Report 结构化状态。

默认不读取 Evidence 正文，更不能读取原始 Session。

## 4. 项目聚合

归属优先级：

1. 明确相同 `project_id`。
2. 相同外部任务/Issue/PR ID 映射到项目。
3. 精确项目别名。
4. 高置信度语义匹配。
5. 独立工作。

低置信度绝不为版面整齐强行归类。`independent_work` 是正式输出，不是失败垃圾桶；保留来源、状态、价值和下一步。

同项目多人内容按“成果、当前状态、决策、风险、依赖、下一步、需要行动”归并。来源引用可追踪；Monitor 输出可以展示每位 Partner 的高层任务进度，但不得展示 Session、Evidence、命令、代码操作明细、消息数量、个人排名或个人 Report 下钻入口。

## 5. 团队状态合并规则

- 同一 Work Item 多人来源使用稳定 ID/外部 ID 合并，保留 contributor report refs。
- 状态冲突不做多数投票；优先时间更新且有明确来源的事件，仍冲突则标记 `needs_attention`。
- Blocker 合并保留影响范围、依赖方和是否解除。
- 重复 Outcome 合并来源，不重复展示。
- 不计算无数据基础的完成百分比。
- 不产生个人排名、贡献分或消息数量对比。

## 6. 跨周期匹配

匹配层级：

```text
same work_item_id
-> same external task/issue/PR id
-> same project_id + high-confidence semantic match
-> unmatched
```

每个 match 输出方法、confidence、当前/上期引用。低置信度保留为本期新增，并在内部标记待确认，不能静默继承上期状态。

## 7. 变化分类

确定性状态规则优先：

| 变化                | 判定示例                            |
| ------------------- | ----------------------------------- |
| `NEW`               | 本期有项，上期无可靠匹配            |
| `PROGRESSED`        | 状态前进或新增实质 Outcome/Decision |
| `COMPLETED`         | 本期 completed 且有来源，上期未完成 |
| `BLOCKED_NEW`       | 本期首次出现未解除 Blocker          |
| `BLOCKED_RESOLVED`  | 上期 Blocker 本期明确解除           |
| `NO_UPDATE`         | 匹配存在但无新事件，达到配置周期数  |
| `SCOPE_CHANGED`     | 目标/范围有明确变更事件             |
| `MILESTONE_DELAYED` | 有明确里程碑变化来源，不由模型猜测  |

禁止通过两期自然语言 Diff 直接判断状态变化。模型可以协助语义匹配和摘要，但最终分类必须引用结构化条件。

## 8. Team Report Draft

至少包含：

```text
team_id, period_id, version
individual_report_ids[]
project_summaries[]
independent_work[]
period_changes[]
risks[]
cross_team_dependencies[]
monitor_actions[]
submission_coverage
data_coverage
source_refs
quality_results
```

`source_refs` 在服务端用于追溯和审计，不作为 Monitor 下钻入口。

## 9. 质量检查

- 每个团队成果至少一个已提交 Report 来源。
- 未提交 Partner 没有内容进入项目摘要。
- 项目/独立工作分类置信度符合阈值。
- 完成、阻塞解除和数字有明确来源。
- 同一 Work Item 没有重复出现在多个项目。
- 风险、依赖和 Monitor Action 没有被摘要丢弃。
- 无个人排名、消息数量或虚构完成百分比。
- 本期和上期使用相同或兼容 Schema；不兼容时显式迁移。

## 10. 重跑与版本

相同输入 checksum 和聚合器版本重复触发返回同一 Run 结果。输入变化、映射修正或算法升级创建新 Team Report 版本，不能覆盖已交付版本。

已交付报告重跑必须走 Admin 明确流程，并产生新版本；是否再次发送由独立交付操作决定。

## 11. 评测与测试

- 2 Partner 同项目合并、1 项独立工作保留。
- 部分 Partner 未提交，不用草稿替代。
- 精确 ID、外部 ID、语义和无匹配四层。
- 新增、推进、完成、新增/解除阻塞、无更新、范围/里程碑变化。
- 项目冲突和低置信度保持独立。
- 相同输入确定性重跑和算法新版本。
- 跨租户/跨团队来源绝不混入。
- 对抗样本验证不生成排名和百分比。

评测重点：错误合并率、变化分类准确率、独立工作保留率、来源覆盖率和摘要事实一致性。

## 12. 验收与退出标准

- 只读取 `SUBMITTED` 报告，未提交成员清晰标记。
- 同项目正确合并，低置信度和独立工作不被强归类。
- 正确识别 AC-10 的五类核心变化，并支持连续阻塞/无更新。
- 不生成无来源百分比或个人排名。
- 每项团队结论可追溯到提交报告和 Snapshot。
- 满足 AC-09、AC-10，输出可供渲染的 Team Report Draft。
