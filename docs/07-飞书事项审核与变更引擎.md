# 07 飞书事项审核与变更引擎

> 当前状态：Review Engine 与数据中台项目卡片一审已经进入主链路；飞书身份、卡片、回调和提醒仍是后续路线。

> 对应 PRD：9.3、10 FR-06/FR-07/FR-12、11、13.1、16.3、16.5、AC-05 至 AC-07。
>
> 前置依赖：03、05、06。

## 1. 目标

当前让 Partner 在数据中台完成项目卡片的确认、修改、排除、恢复、重点、项目、状态、合并、拆分、补充和时间范围调整。所有变更必须先生成结构化 Preview，再由 Partner 明确 Apply。未来飞书只复用同一个 Review Engine，不建立第二套审核状态。

## 2. 组件

| 组件                   | 职责                                     |
| ---------------------- | ---------------------------------------- |
| Review Engine          | 审核状态、进度、版本和守卫条件           |
| Change Parser          | 把表单/自然语言解析为结构化操作          |
| Change Planner         | 校验权限、事实充分性和是否需 Re-analysis |
| Preview Renderer       | 生成人可读前后差异                       |
| Change Applier         | 事务应用、乐观锁和审计                   |
| Feishu Gateway         | 验签、快速 ACK、消息/卡片发送和更新      |
| Card Renderer          | 总览、单项、Preview、完成和错误状态模板  |
| Notification Scheduler | 首次通知、提醒、去重和停止提醒           |

## 3. Review 状态

```text
PENDING -> IN_PROGRESS -> ITEMS_APPROVED
   |            |-> WAITING_LOCAL_REANALYSIS -> IN_PROGRESS
   |            |-> CHANGE_PREVIEW_PENDING -> IN_PROGRESS
   |-> CANCELLED
```

Review 保存 `version`、当前 item cursor、已确认/排除/待确认计数和最后活动时间。Work Item 修改会递增对象与 Review 版本。

## 4. 飞书回调入口

`POST /v1/integrations/feishu/card-actions`

同步路径只做：

1. 验证飞书签名、防重放和事件时间。
2. 解析 `tenant/partner/review/item/base_version/action`。
3. 校验 `feishu_open_id` 与 Partner Binding。
4. 持久化回调事件并按事件 ID 去重。
5. 快速返回“已接收”。

LLM、聚合、重分析或卡片复杂更新进入 Worker。目标是用户 2 秒内看到接收反馈，而不是 2 秒内完成全部业务。

## 5. 卡片状态

实现 PRD 中五类卡片：

- Work Item 总览。
- 单个 Work Item。
- 修改表单。
- Change Preview。
- 审核完成/生成 Report 入口。

附加状态：处理中、等待本地 Codex、版本过期、操作失败可重试、Review 已关闭。

一张卡片只保留一个主任务。超过 8 至 10 项时分批；MVP 可以提供只读 Web 详情页，但不把批量编辑工作台混入本板块。

## 6. 结构化变更协议

```json
{
  "review_id": "review_123",
  "work_item_ids": ["wi_123"],
  "base_version": 2,
  "operation": "update_status",
  "value": "completed",
  "scope": "current_period",
  "source": "feishu_natural_language"
}
```

支持操作：`approve`、`exclude`、`restore`、`update_fact`、`add_fact`、`set_emphasis`、`assign_project`、`update_status`、`merge`、`split`、`change_period`。

Parser 输出必须通过操作级 Schema，并给出置信度和歧义字段。低置信度或缺必要对象时请求 Partner 澄清，不猜测执行。

## 7. Preview/Apply

### 7.1 Preview

`POST /v1/reviews/{id}/changes/preview`

执行：权限 -> base version -> 操作验证 -> 来源充分性 -> 影响计算 -> 是否需重新分析。Preview 保存不可变 `change_id`、before/after、影响 Work Item、过期时间和基准版本。

### 7.2 Apply

`POST /v1/reviews/{id}/changes/apply`

在单事务中：

1. 锁定 Review/Work Item 当前版本。
2. 校验 Preview 未过期且基准未变化。
3. 应用结构化操作并递增版本。
4. 保存 ReviewChange 前后差异和来源。
5. 发布重新聚合/卡片更新事件。

相同 `change_id` 重复 Apply 返回第一次结果。版本冲突不自动重放，卡片显示刷新提示。

## 8. 事实修改与 Re-analysis 判定

可以直接服务端处理：已有 Fact 支持的重组、Partner 明确补充、项目/重点/表达元数据修改。

必须创建 Re-analysis：扩大到未同步日期、要求深挖原始聊天、现有证据不足、指定新 extractor version。

等待期间原 Review 保持可读，受影响项不可被误标确认。任务完成后生成新 Preview，由 Partner 再次确认。

## 9. 合并、拆分与排除

- Merge Preview 展示主项、被合并项、Fact 集、状态冲突和最终标题；Apply 写 lineage。
- Split 必须让 Partner 指定 Fact/事件归属或提供清晰规则；不明确时进入 Web 详情或逐项选择。
- Exclude 从当前报告投影移除，不物理删除 Fact；敏感信息排除同时创建删除/清理任务。
- Restore 只对未被隐私删除且仍在授权范围的事项开放。

## 10. 审核完成守卫

只有以下条件全部满足，才能创建 `WorkItemSnapshot`：

- 所有必审项为 approved 或 excluded。
- 无进行中的 Preview、Re-analysis 或解析澄清。
- 每个 completed 项有 Evidence 或 Partner supplied fact。
- Coverage Snapshot 已生成，Warning 会进入报告。
- Review 当前版本与卡片操作版本一致。

## 11. 通知与提醒

- 周期结束和初次聚合完成后发送一次总览。
- 截止前按 Team Policy 提醒未完成 Partner。
- 已提交、已撤销绑定或 Review 关闭后停止提醒。
- 去重键：`tenant + partner + period + notification_type + policy_slot`。
- 卡片发送/更新失败可重试，成功外部消息 ID 持久化。

## 12. 测试

- 飞书签名错误、重放、重复回调和身份不匹配。
- 旧卡片 `base_version` 冲突。
- 所有操作的 Preview、取消和 Apply。
- 自然语言多意图、歧义、恶意指令和超范围对象。
- 相同 `change_id` 重复 Apply。
- merge/split 的 Fact 不丢失，排除/恢复行为正确。
- 需要 Re-analysis 时不提前改数据。
- 提醒去重、提交后停止和卡片更新失败恢复。
- Partner A 无法构造回调修改 Partner B 的 Review。

## 13. 指标与审计

指标：回调 ACK 延迟、处理成功率、卡片更新失败、Review 完成时间、每项修改率、Parser 澄清率、版本冲突、Re-analysis 触发率、提醒转化。

审计：回调接收、Preview 创建/取消/应用、before/after、Partner 补充来源、Evidence 访问、merge/split/exclude、审核完成。

## 14. 验收与退出标准

- Partner 可在飞书完成 PRD AC-05 的全部必要操作。
- 每个修改先展示前后差异，取消不改变数据。
- 旧卡片不能覆盖新版本。
- 自然语言只生成结构化操作，歧义不静默执行。
- Re-analysis 等待/失败/完成状态真实可见。
- 审核完成生成不可变 Snapshot，并满足 AC-06、AC-07。
