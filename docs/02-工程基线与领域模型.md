# 02 工程基线与领域模型

> 对应 PRD：5、7、12 至 18、FR-13、NFR-01 至 NFR-05。
>
> 前置依赖：01 技术预研与可行性验证。

## 1. 目标

建立所有后续模块共享的工程骨架、领域语言、数据 Schema、状态机、异步任务规范和测试基线。该板块完成后，Plugin、后端、飞书和报告引擎可以围绕同一套版本化契约并行开发。

## 2. 工程结构

具体语言和框架由 ADR 决定，逻辑边界固定为：

```text
contracts/        # JSON Schema、API 和事件契约
plugin/           # Codex 本地 Plugin
service/
  identity/       # 租户、主体、绑定
  ingestion/      # Fact 接收与 Coverage
  work-items/     # 聚合、排序、快照
  reviews/        # 审核和变更
  reports/        # 个人/团队报告
  integrations/  # 飞书
  governance/     # 审计、保留、删除
workers/          # 异步任务执行
evaluation/       # AI 和匹配评测
tests/            # 契约、集成、E2E
```

部署可以先采用模块化单体加独立 Worker，但模块之间必须通过明确接口协作，禁止跨模块直接修改对方数据表。

## 3. 统一标识与租户边界

所有领域对象使用不可复用的内部 ID，并始终包含 `tenant_id`：

```text
tenant_id
team_id
partner_id
plugin_instance_id
period_id
session_id
fact_id
work_item_id
review_id
snapshot_id
report_id
team_report_id
artifact_id
delivery_id
```

约束：

- 外部 ID（如 `feishu_open_id`、Issue ID）不能作为数据库主键。
- 唯一索引必须带 `tenant_id`。
- API 从认证上下文取得 `tenant_id`，不信任请求体单独声明的租户。
- 队列消费者在执行业务逻辑前再次校验消息租户与目标对象租户一致。

## 4. 核心实体

除 PRD 已给出的模型外，v1 需要补齐以下实体：

| 实体 | 关键字段 | 关键约束 |
| --- | --- | --- |
| `ReportPeriod` | team、type、start/end、timezone、cutoff | 时间范围不可变；调整创建新配置版本 |
| `PluginInstance` | partner、device、version、status、last_seen_at | MVP 每个 Partner 最多一个 active 实例 |
| `SessionFact` | session、schema/extractor version、fact payload、evidence | 相同来源版本幂等 |
| `SyncBatch` | instance、counts、status、idempotency key | 支持部分成功和重试 |
| `CoverageSnapshot` | period、discovered/read/extracted/failed/excluded | 各数量可解释且总数一致 |
| `WorkItemSnapshot` | work item version、fact refs、approved_at | 创建后不可修改 |
| `Review` | subject type/id、state、version、actor | 一次审核只绑定一个周期和 Partner |
| `ReanalysisJob` | scope、reason、lease、attempt、status | 幂等领取、租约超时、可取消 |
| `AuditEvent` | actor、action、target、before/after ref、request id | 追加写，不原地覆盖 |
| `Artifact` | report version、format、checksum、storage key | 内容与报告版本一一对应 |
| `DeliveryAttempt` | target、artifact、idempotency key、external ids、status | 一条成功终态，多次尝试可追踪 |

Evidence 正文与业务 Fact 分离存储，以便独立授权、保留和删除。

## 5. 状态机

### 5.1 Session 处理状态

```text
DISCOVERED -> DIRTY -> READY_FOR_EXTRACTION -> EXTRACTING
-> EXTRACTED -> SYNC_PENDING -> SYNCED
```

异常分支：`READ_FAILED`、`EXTRACTION_FAILED`、`SYNC_FAILED`、`EXCLUDED`。失败可回到最近的可重试状态；`EXCLUDED` 只有 Partner 或授权规则变更才能恢复。

### 5.2 个人报告状态

沿用 PRD：

```text
COLLECTING -> EXTRACTING -> ITEM_REVIEW_PENDING
-> ITEM_REVIEW_IN_PROGRESS -> ITEM_APPROVED
-> REPORT_DRAFT -> REPORT_REVIEW -> SUBMITTED -> LOCKED
```

允许的回退必须显式创建版本或任务，禁止直接改状态字段绕过守卫条件。

### 5.3 团队报告状态

实施基线：

```text
WAITING_SUBMISSIONS -> AGGREGATING -> TEAM_DRAFT
-> READY_FOR_DELIVERY -> DELIVERING -> DELIVERED
```

失败状态为 `GENERATION_FAILED`、`RENDER_FAILED`、`DELIVERY_FAILED`，均保留可重试来源状态。PRD 中的 `MONITOR_REVIEW` 不进入实现，因为 Monitor 明确不参与审核。

## 6. 契约版本

每个跨边界 Payload 至少携带：

```json
{
  "schema_version": "1.0",
  "producer_version": "...",
  "tenant_id": "...",
  "occurred_at": "...",
  "request_id": "..."
}
```

版本策略：

- 同一主版本内只允许向后兼容地新增可选字段。
- 删除、改名、语义变化需要新主版本。
- 服务端至少接受当前和前一个兼容版本，并对旧 Plugin 返回升级提示。
- Schema、示例和验证器从同一源生成，禁止手写多份定义。

## 7. API 基线

统一规则：

- HTTPS JSON；批量上传可启用压缩。
- 写请求使用 `Idempotency-Key`，响应回显请求 ID 和资源版本。
- 错误返回稳定 `code`、用户安全的 `message`、是否可重试和字段级详情。
- 列表使用游标分页。
- 变更请求使用 `base_version`；冲突返回 `409 VERSION_CONFLICT`。
- 异步请求返回任务 ID，不在 HTTP/飞书回调中等待 LLM 或渲染完成。

建议错误码：`UNAUTHENTICATED`、`FORBIDDEN`、`TENANT_MISMATCH`、`SCHEMA_UNSUPPORTED`、`VERSION_CONFLICT`、`COVERAGE_INCOMPLETE`、`REANALYSIS_REQUIRED`、`RATE_LIMITED`、`DEPENDENCY_UNAVAILABLE`。

## 8. 事件与任务基线

至少定义以下领域事件：

```text
plugin.binding.activated
plugin.binding.revoked
session.facts.ingested
coverage.snapshot.updated
work_items.draft.created
review.change.applied
work_items.snapshot.approved
individual_report.submitted
team_report.ready_for_delivery
team_report.delivered
deletion.requested
```

消费者保证至少一次处理，因此每个 Handler 必须基于事件 ID 或业务幂等键去重。任务记录持久化状态、尝试次数、下次重试时间、错误分类和关联对象。

## 9. 数据库与迁移

- 使用迁移工具管理 Schema，不允许应用启动时静默改表。
- 生产迁移必须可前向兼容上一版本应用，采用扩展/迁移/收缩步骤。
- 不可变 Snapshot、AuditEvent 和 DeliveryAttempt 采用追加写。
- JSON Payload 保留原 Schema 版本，同时将高频查询字段规范化为列。
- 所有租户查询建立复合索引，并通过查询测试防止遗漏租户条件。

## 10. 基础设施能力

本板块交付：

- 配置加载与环境校验。
- 数据库、队列、对象存储适配层。
- 结构化日志、Trace/Request ID 传播。
- 指标注册和健康检查。
- 密钥管理接口，不在配置文件中保存生产密钥。
- 测试容器或等价本地集成环境。
- CI：格式、静态检查、单元测试、Schema 兼容性、迁移测试和秘密扫描。

## 11. 测试

必须覆盖：

1. JSON Schema 正反例和兼容性。
2. 所有状态机的允许/禁止转换。
3. 相同幂等键重复调用返回同一效果。
4. 乐观锁冲突不会覆盖新版本。
5. 所有仓储查询均隔离租户。
6. 事件重复、乱序和消费者重启。
7. UTC 存储与 Team 时区周期边界，包括夏令时地区。
8. 迁移从空库和上一版本升级。

## 12. 退出标准

- 领域词汇、ID、状态机和 v1 Schema 经后端、Plugin、AI、飞书团队共同评审。
- 基础服务和 Worker 可以启动，健康检查、数据库、队列和对象存储可用。
- 契约测试能被 Plugin 和服务端共同执行。
- 租户隔离、幂等、乐观锁和状态守卫测试通过。
- CI 能阻止不兼容 Schema、失败迁移和敏感信息进入仓库。
- 00 文档中的状态机冲突已形成正式 ADR。
